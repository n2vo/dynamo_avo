### Findings Log

Each milestone closes with one entry: The benchmark, the bottleneck that limits throughput or latency, the evidence, and the fix or the reason it was deferred, followed by the comparison against the Dynamo counterpart.

#### Milestone 1: Block Hashing

- **Benchmark:** `benches/hashing.rs`, Criterion, group `plh`, block size 16, unsalted, 1,024 / 8,192 / 32,768 tokens, on jeeves7 (M1 Max). Dynamo baseline times only `Request::positional_lineage_hashes(16)` on a prebuilt `Request`. Results in millions of tokens per second (Melem/s): Dynamo 260 to 275; `hash_sequence` 459 to 464; `IncrementalHasher` 252 to 268. Flat across lengths.
- **Bottleneck:** `IncrementalHasher::push` runs at about 0.57x of `hash_sequence` on the same tokens. Both share `chain_step` and `token_bytes`, so the difference is per-token entry cost: One bounds-checked `Vec::push`, one length compare, one branch, per token, versus one `chunks_exact` step per block. Hypothesis from code reading; not isolated by measurement.
- **Evidence:** Same outputs proven by the differential tests against `dynamo-kv-hashing` 1.5.1 and by the `incremental_matches_one_pass` proptest. Moving the token clone and `Request` build out of the Dynamo timed region changed its throughput by 2 to 4 percent, so the remaining gap is inside `into_blocks`.
- **Fix or Deferral:** Deferred. Decode produces one token per step, so the per-token path is the real one; batching through an `extend` would only help prefill. Candidate fixes: Replace the `Vec<u8>` allocation in `token_bytes` with a stack buffer sized by block, and let `push` write the token's bytes directly into that buffer instead of staging `u32` values. Revisit when a milestone exercises the decode path end to end.
- **Dynamo Comparison:** The xxh3 work is identical: Two hashes per block, same seeds, same little-endian layouts. The 1.7x throughput gap is structural, not algorithmic. `into_blocks` clones the full token vector, builds a `TokenBlockSequence` with one `TokenBlock` per block, each owning a copy of its tokens and both hashes, collects a `Vec<UniversalBlock>`, and then maps that into the returned hashes. Dynamo materializes block objects because its router, pool, and migration paths consume them; the hash is a by-product. `avo-kv-hash` computes only the hash. When later milestones require block objects, that cost returns.

#### Milestone 2: Block Pool

- **Benchmark:** `benches/pool.rs`, Criterion, group `pool`, capacities 1,024 / 8,192 / 32,768 blocks, on jeeves7 (M1 Max). `alloc_drop` allocates and drops an uncommitted block (free-list path). `lookup_hit` looks up a committed inactive block and drops the handle (hash-index path). `evict` allocates on a pool whose blocks are all inactive, so every allocation evicts, then commits under a fresh hash and drops. Medians after the fix: `alloc_drop` 20.5 ns; `lookup_hit` 24.6 ns; `evict` 66.8 ns, 66.9 ns, and 71.4 ns.
- **Bottleneck:** The first implementation found the least recently used (LRU) block by scanning every entry of `blocks` for the smallest `last_use`, so eviction was O(n) in capacity at about 0.7 ns per block: 762 ns, 6.06 µs, and 23.1 µs at the three capacities. At 32,768 blocks one eviction cost as much as about 1,100 free-list allocations, and once the pool fills, every allocation evicts.
- **Evidence:** Before the fix, eviction time grew 7.95x for an 8x increase in capacity and 3.81x for 4x, while the free-list and lookup paths stayed flat. Pool correctness under random allocate, commit, lookup, clone, and drop sequences is proven by `no_block_leaked_or_freed_twice`. During the fix it caught a missing link update in `lru_unlink`; the failing sequence is saved in `properties.proptest-regressions` and replays on every run.
- **Fix or Deferral:** Fixed. Inactive blocks are kept in an intrusive doubly linked list indexed by block id (`prev`, `next`, `head`, `tail`): release appends at the tail, a lookup hit unlinks from anywhere, and eviction pops the head, all O(1) with no allocation. Eviction is now flat at 67 to 71 ns, 11x to 323x faster. The cost is about 2 ns on `lookup_hit` (22.5 to 24.6 ns), one unlink and one push per revive. The same change fixed a stale-index bug: Evicting a block deleted the hash-index entry unconditionally, so if a newer block had been committed under the same hash, its entry was removed and it became unreachable. Eviction now removes the entry only if it still points at the evicted block; `evicting_a_replaced_block_keeps_the_newer_index_entry` covers it.
- **Dynamo Comparison:** Dynamo `main` at `4435cab`, `lib/kvbm-logical/src/pools/inactive`. The inactive pool is pluggable: HashMap with first-in-first-out (FIFO) reuse (`BTreeMap`, O(log n)), LRU (`lru` crate, O(1) `pop_lru`), multi-LRU (four LRU tiers bucketed by TinyLFU access frequency, coldest tier evicted first), and Lineage. The default when none is configured is Lineage with Tick ordering, which evicts only leaves of the prefix lineage graph, ordered in a `BTreeMap` by insertion tick (O(log n)); a Fifo variant is O(1) with no steady-state allocation, the same shape as the list here. No backend scans. The remaining difference is leaf-only eviction: `avo-block-pool` can evict a parent block while its children stay cached, and because prefix matching stops at the first miss, those children become unreachable while still holding capacity. Leaf-only eviction now exists in Milestone 3's radix index, over index entries; `avo-block-pool` itself still evicts by LRU without regard to lineage.

#### Milestone 2: Block Pool Concurrency

- **Benchmark:** `benches/contention.rs`, Criterion, group `contention`, 1 / 2 / 4 / 8 threads on a 4,096-block pool, on jeeves7 (M1 Max). `churn`: Each thread allocates (evicting once the pool is full), commits under a thread-unique hash, and drops. `lookup`: Each thread looks up one of 1,024 shared committed blocks and drops the handle. `churn_batch8`, `churn_batch32`, `lookup_batch8`, `lookup_batch32`: The same cycles in batches of 8 or 32 blocks, with one `allocate_many` and one `commit_many`, or one `lookup_prefix` over consecutive shared hashes, per batch; each handle drop still takes the lock. One element is one block cycled by one thread and time runs from barrier release to the last join, so results are total throughput across threads; ideal scaling doubles when threads double. Medians with `std::sync::Mutex`, in millions of cycles per second: `churn` 15.0, 8.19, 4.67, 3.82; `lookup` 39.5, 16.8, 7.44, 7.47.
- **Bottleneck:** One `Mutex<PoolState>` guards the whole pool, and every operation takes it: `allocate`, `commit`, `lookup`, `hash`, and every handle clone and drop. Total throughput falls as threads are added instead of rising: 3.9x lower for `churn` and 5.3x lower for `lookup` at 8 threads than at 1. The pool serializes on the lock, and the added threads pay handoff cost on top.
- **Evidence:** The same decline at every step from 1 to 4 threads on both workloads, with `lookup` flat from 4 to 8, is inferred as the signature of a single contended lock rather than of the work inside it; the single-thread paths measure 20 to 25 ns in `benches/pool.rs`. Correctness under contention is proven by `invariants_hold_under_concurrent_use`: Eight workers run 20,000 seeded operations each over 32 shared hashes on a 64-block pool while a checker thread audits the free, active, inactive partition under the lock, and nothing is active after every handle drops. The first version of that test hung instead of failing when a worker panicked, because the checker was never told to stop; the fixed version joins every worker, stops the checker, then re-raises the first worker panic with `resume_unwind`. With an injected bug it fails in under a second.
- **Fix or Deferral:** Fixed in two steps. Step 1: `std::sync::Mutex` replaced by `parking_lot::Mutex`, which also removes the poison-recovery path in `lock`, since `parking_lot` has no lock poisoning. Medians after: `churn` 18.1, 12.7, 9.26, 4.04; `lookup` 51.1, 24.0, 17.3, 11.8. Gains of 1.21x, 1.56x, 1.98x, 1.06x for `churn` and 1.29x, 1.43x, 2.33x, 1.58x for `lookup`. The collapse remains: 1 to 8 threads still falls 4.5x for `churn` and 4.3x for `lookup`, and `churn` at 8 threads is within noise of before, because the lock is cheaper to take but still taken once per operation. Why `parking_lot` gains most at 4 threads was not isolated by measurement. Step 2: Batch APIs that take the lock once per call: `allocate_many(n)` (all or nothing), `lookup_prefix(&[u64])` (stops at the first miss), and `commit_many` (validates the whole batch before applying any of it). Measured back to back against `main` with the hash index hasher (Milestone 2: Block Pool Hash Index), in millions of blocks per second at 1, 2, 4, 8 threads: `churn_batch8` 26.1, 17.2, 12.9, 5.97 and `churn_batch32` 28.5, 18.4, 13.4, 7.04 against `churn` 31.3, 17.9, 11.4, 4.83; `lookup_batch8` 45.6, 29.1, 23.2, 14.4 and `lookup_batch32` 49.5, 30.3, 21.3, 16.0 against `lookup` 51.6, 23.3, 16.7, 12.0. Batching is 4 to 17% slower at 1 thread, where the lock is uncontended and each call allocates (`Vec`s, and a `HashSet` in `commit_many`); that cost was not measured separately. At 2 threads it ranges from 0.96x to 1.30x, and at 4 and 8 threads it gains 1.13x to 1.46x; an 8-thread repeat in swapped order agreed within 3%. The collapse is smaller but remains: 1 to 8 threads falls 4.0x for `churn_batch32` and 3.1x for `lookup_batch32`, against 6.5x and 4.3x single-block, because each handle drop still takes the lock once per block. Before the hasher, the restructured single-block paths regressed by 22 to 27% at 1 thread (`lookup_hit` +6.4 ns and `evict` +15 to 20 ns in `benches/pool.rs`); in x86 machine code SipHash was compiled as a separate call on those paths, and with the hasher the regression is gone, but the M1 machine code was not inspected. Moving handle reference counts off the lock is not planned.
- **Dynamo Comparison:** Dynamo `main` at `4435cab`. `BlockStore` (`lib/kvbm-logical/src/pools/store.rs`) has the same shape: All state behind one `parking_lot::Mutex` (`inner: Mutex<BlockStoreInner<T>>`). Dynamo's lever is batching, not a finer lock: `match_blocks` in `lib/kvbm-logical/src/manager/mod.rs` takes one store-lock acquisition for an entire active plus inactive prefix through `BlockStore::match_prefix_locked_batch`, a scattered variant does the same for non-prefix probes, and TinyLFU frequency updates run outside the lock. Dynamo's handles also avoid the store lock on clone and take it only when the last reference drops. Step 1 here matches Dynamo's lock; step 2 matches its batching.

#### Milestone 2: Block Pool Hash Index

- **Benchmark:** `benches/pool.rs` (single thread: `alloc_drop`, `lookup_hit`, `evict` at 1,024, 8,192, and 32,768 blocks) and the `churn` and `lookup` workloads of `benches/contention.rs` (1 / 2 / 4 / 8 threads, 4,096 blocks), on jeeves7 (M1 Max), measured back to back against `main` on November 17, 2026.
- **Bottleneck:** The hash index (`by_hash`, block hash to block id) used the standard `HashMap` hasher, SipHash-1-3 with a random key, and every lookup, eviction, and commit hashes under the pool lock: `lookup` once per operation, `churn` three times per cycle (`get` and `remove` on eviction, `insert` on commit).
- **Evidence:** In `benches/pool.rs`, `evict` falls from 56.5, 57.6, and 66.0 ns to 31.3, 32.2, and 34.7 ns at 1,024, 8,192, and 32,768 blocks, while `alloc_drop` (about 20 ns) and `lookup_hit` (19.4 to 19.5 ns) are unchanged. Over three back-to-back pairs, `churn` gains 1.73x to 1.75x at 1 thread, 1.37x to 1.59x at 2, 1.04x to 1.48x at 4, and 1.19x at 8; medians after are 31.4 to 31.9, 16.8 to 17.9, 8.52 to 11.4, and 4.71 to 4.82 million cycles per second. The 4-thread case varies most between runs on this machine. `lookup` is unchanged (51.2, 24.3, 16.8, 11.7 before; 50.8, 24.1, 16.8, 11.9 after): On this machine one SipHash per operation showed no measurable cost. Found while bisecting a single-thread regression in the batch API work; that regression is recorded with that work.
- **Fix or Deferral:** Fixed. `by_hash` uses `BlockHashHasher`, one multiply by 2^64 / golden ratio (Fibonacci hashing), which keeps sequential keys spread across the top 7 bits that `hashbrown` stores as slot tags. The lock is still taken once per operation, so the Block Pool Concurrency collapse remains and steepens: `churn` falls 6.5x to 6.8x from 1 to 8 threads, up from 4.5x, because each operation is shorter.
- **Dynamo Comparison:** Dynamo `main` at `4435cab`. Dynamo's hash-keyed maps also skip SipHash: `SeqHashMap` in `lib/kvbm-logical/src/pools/mod.rs` uses `IdHasher`, which folds the already-mixed 128-bit sequence hash to 64 bits with one XOR, because these lookups run under the store mutex. Keys here are raw `u64` values, sequential in the tests and benchmarks, so this pool adds the multiply that Dynamo's identity hasher does not need.

#### Milestone 3: Radix Index

- **Benchmark:** `crates/avo-radix-index/benches/radix_bench.rs`, Criterion, group `radix`, on jeeves7 (M1 Max). Workloads of 1,000 sequences of 64 blocks and 10,000 sequences of 256 blocks, with the first 0, 50, or 90 percent of every sequence identical (a shared system prompt) and the rest unique. `build_radix` and `build_flat` insert every sequence into an empty index (one element is one block); `match_radix` and `match_flat` find the longest stored prefix of one stored sequence, round robin (one element is one query); `evict_radix` evicts every block from a built tree (one element is one block). `FlatHashIndex` is one `HashMap` entry per chained block hash, probed block by block until the first miss.
- **Bottleneck:** A flat index keyed by chained hash costs one hash lookup per block, both to insert and to match, so a 256-block prompt is 256 lookups even when 230 of its blocks are a prefix every request shares. It also has no notion of which blocks other sequences pass through, so it cannot evict without risking a shared prefix.
- **Evidence:** Index sizes are exact and identical on any machine: Distinct blocks stored are the same in both indexes (2,560,000, 1,280,128, and 260,230 for the 10,000-by-256 workloads at 0, 50, and 90 percent shared); the tree adds one child-map entry per node (10,001 or 10,002 nodes), under 4 percent more entries at 90 percent shared. Medians on jeeves7, at 0, 50, and 90 percent shared: For 1,000 sequences of 64 blocks, `build_radix` 264, 192, and 203 million blocks per second against `build_flat` 17.2, 25.5, and 41.4 (15.3x, 7.5x, 4.9x), and `match_radix` 190, 315, and 303 ns per query against `match_flat` 666, 609, and 594 ns (3.5x, 1.9x, 2.0x). For 10,000 sequences of 256 blocks, `build_radix` 529, 435, and 460 against `build_flat` 15.3, 24.7, and 38.4 (34.6x, 17.6x, 12.0x), and `match_radix` 409, 535, and 549 ns against `match_flat` 11.0, 5.65, and 2.96 µs (26.9x, 10.6x, 5.4x). `evict_radix` runs at 23.5 to 28.9 million blocks per second across all six workloads. The tree's advantage is largest with no sharing and shrinks as sharing grows. The tree hashes once per edge, so an unshared 256-block sequence costs one hash and one contiguous slice comparison, and sharing adds a hop and an edge split. The flat index gets faster as sharing grows, likely because it holds fewer distinct entries (260,230 against 2,560,000) and fits better in cache; that cause was not measured.
- **Fix or Deferral:** Fixed for a single thread: A compressed radix tree whose edges hold runs of blocks, so a shared prefix is one hop and one slice comparison. Insert splits an edge where a sequence diverges partway along it and extends a leaf in place rather than hanging a single child. Eviction removes the last block of the least recently used unpinned leaf, never a block another stored sequence passes through, frees an emptied leaf, and merges a parent left with one child, so no dead or single-child internal node remains. Pins protect a sequence and its prefix. Each block carries a tier tag (`Tier1Device`, `Tier2PinnedHost`, `Tier3DiskOrRemote`) for the Milestone 4 spill policies. The proptest checks every match against a brute-force map of all stored prefixes and bounds the node count by blocks and by leaves; six injected bugs (no compaction, evicting internal nodes, ignoring pins, not recording access, splitting at the wrong offset, block-count drift) each fail at least one test. Concurrency is deferred.
- **Dynamo Comparison:** Dynamo `main` at `35e2a66`. The router's tree is `lib/router/kv-indexer/src/concurrent_radix_tree_compressed` (moved there from `lib/kv-router/src/indexer` in #18055): Concurrent, built from worker KV events, and tracking which workers hold each block; it does not evict pool capacity. Leaf-only eviction is the block manager's Lineage backend, `lib/kvbm-logical/src/pools/inactive/backends/lineage`, ordered by an insertion tick in a `BTreeMap`. This crate combines the two in one single-threaded structure: An LRU `BTreeSet` keyed by last-access tick, over leaves only, with one owning worker per block rather than a set of workers.

#### Milestone 4: KV Offload & Tiering

- **Benchmark:** `crates/avo-kv-offload/benches/offload_bench.rs`, Criterion, group `offload`, disk configurations (filter `^offload/disk`), flushing 64 MiB and 256 MiB of 32 KiB KV blocks to one file in the system temporary directory, through the page cache with no `fsync`, on jeeves7 (M1 Max). Compares `UnalignedBlockWriter` (one write per block) against `CoalescedSlabWriter` with 1, 2, and 4 MiB slabs, each written once and padded to 4,096 bytes. Medians from the third of three runs, at 64 MiB: `disk_unaligned` 19.36 ms (3.23 GiB/s); `disk_slab_1m` 10.83 ms (5.77 GiB/s, 1.79x faster); `disk_slab_2m` 10.48 ms (5.96 GiB/s, 1.85x); `disk_slab_4m` 10.73 ms (5.83 GiB/s, 1.80x). At 256 MiB: `disk_unaligned` 74.43 ms (3.36 GiB/s); `disk_slab_1m` 47.05 ms (5.31 GiB/s, 1.58x); `disk_slab_2m` 86.19 ms (2.90 GiB/s, 0.86x); `disk_slab_4m` 85.89 ms (2.91 GiB/s, 0.87x).
- **Bottleneck:** The per-block writer issues one write per block: 2,048 writes for 64 MiB and 8,192 for 256 MiB, against 64 and 256 with 1 MiB slabs. One isolated 32 KiB write measured 3.3 µs in `flush_one`, about a third of the 9.1 to 9.5 µs per block in the third run's `disk_unaligned`, so the write call alone does not account for the per-block cost; the remainder was not isolated. At 64 MiB, coalescing was 1.79x to 1.97x faster at every slab size in all three runs. At 256 MiB the disk results are not stable between runs: 2 MiB slabs measured 44.07, 44.10, and 86.19 ms, and 4 MiB slabs 56.89 (50.54 on a rerun), 53.09, and 85.89 ms, so only in the third run were 2 MiB and 4 MiB slabs slower than per-block writes. Hypothesis, not measured: Each iteration truncates the same file and writes through the page cache without `fsync`, so data from earlier iterations may still be draining to the SSD during later timed iterations; in the third run the slowdown grew in run order (1 MiB +7%, 2 MiB +65%, 4 MiB +74% against the previous run).
- **Evidence:** Round-trip bit-for-bit integrity on the host DRAM and disk tiers, 4,096-byte alignment of every write offset and length, batches that fill more than one slab (no block is split across slabs), and bounded-queue backpressure (`RejectWhenFull` and `DropOldestCold`) are proven by the proptests and unit tests in `tests/proptest_offload.rs`, alongside `avo-obs` trace-field checks; seven injected bugs each fail at least one test. The host tier uses the same slab writer and slab buffers, and its 2 MiB and 4 MiB slabs at 256 MiB stayed at 11.76 to 12.89 ms (19.4 to 21.3 GiB/s) across two runs, so slab buffer allocation and copying do not explain the disk results.
- **Fix or Deferral:** Complete for Milestone 4. The 256 MiB disk ranking is deferred until the benchmark controls page-cache state. No slab size is a demonstrated optimum: 2 MiB was fastest on the host tier at both sizes in both runs, and on disk at 64 MiB in two of three runs. Next measurement: A fresh file per iteration and `sync_all` inside the timed region, so disk results include the device write. Candidate fixes after that: Bypass the page cache with `F_NOCACHE` (macOS) or `O_DIRECT` (Linux), where `O_DIRECT` also requires page-aligned buffer memory, not only page-aligned offsets and lengths; and reuse slab buffers instead of allocating one `Vec` per slab.
- **Dynamo Comparison:** Dynamo `main` at `35e2a66`, [`lib/kvbm-engine/src/offload`](https://github.com/ai-dynamo/dynamo/tree/35e2a66a01/lib/kvbm-engine/src/offload). `OffloadEngine` runs asynchronous pipelines G1 to G2 (host memory), G2 to G3 (disk or NVMe), and G2 to G4 (object storage such as S3). In each pipeline a `BatchCollector` flushes when a batch reaches `max_batch_size` (default 1,024 blocks) or when `flush_interval` (default 10 ms) expires with at least `min_batch_size` (default 8) blocks; the input queue is a lock-free crossbeam `SegQueue` that supports cancellation by sweeping. Alignment in Dynamo is applied to memory region addresses: [`lib/kvbm-physical/src/layout/builder.rs`](https://github.com/ai-dynamo/dynamo/blob/35e2a66a01/lib/kvbm-physical/src/layout/builder.rs) rounds each region start up with `align_up`. Dynamo batches blocks per transfer and bounds batching latency with `flush_interval`; this crate batches bytes per storage write (one write per slab), aligns storage offsets and lengths rather than memory addresses, bounds its queue with an explicit backpressure rule, has no flush deadline, and is synchronous and single-threaded.

#### Milestone 5: KV Router

- **Benchmark:** `crates/avo-kv-router/benches/router_bench.rs`, Criterion, on jeeves7 (M1 Max). Group `router`: `select_worker` latency. `kv_aware` over 8, 32, and 128 workers, 64 and 256 block requests, and 0, 50, and 90 percent of the request already cached on every worker (each worker caches four requests that share that prefix with the query); `round_robin` and `least_loaded` at 256 blocks and 50 percent. Group `router_workload`: One 1,000-request run per policy over 8 simulated workers. Each request is one of 32 shared prompts of 48 blocks plus 16 blocks of its own; each worker caches up to 1,024 blocks with leaf-only least recently used (LRU) eviction, the blocks of the 32 most recent requests stay pinned and count as allocated, and every block a worker stores or evicts reaches the router as an event. Weights are `prefill_weight` 1.0 and `load_weight` 64.0, so a full worker costs as much as prefilling one 64-block request; `kv_aware` also runs with `load_weight` 0.
- **Bottleneck:** The router keeps one radix tree per worker, so `kv_aware` matches the request against every eligible worker: One traversal per worker, each comparing every matched block hash along its edges. Selection cost therefore grows with workers times matched blocks. `round_robin` matches only the chosen worker, and `least_loaded` scans worker loads without matching.
- **Evidence:** Prefill blocks in `router_workload` are printed by the benchmark and are identical on any machine, since the workload is seeded and contains no timing. Out of 64,000 prompt blocks: `kv_aware` with `load_weight` 64 prefilled 17,584 (27.5%); with `load_weight` 0, 17,536 (27.4%), the minimum for this workload (16,000 unique tail blocks plus 48 blocks for each of 32 prompts once); `round_robin` 42,928 (67.1%); `least_loaded` 43,872 (68.5%). KV-aware routing prefilled 2.44x fewer blocks than round robin. The cost is balance: Peak load ratio was 0.750 (`load_weight` 64) and 0.812 (`load_weight` 0) against 0.312 for both baselines, and no request was rejected. Estimates on jeeves7, `select_worker`: `kv_aware` at 256 blocks and 0 / 50 / 90 percent, 8 workers 99.9 ns / 1.39 µs / 2.11 µs, 32 workers 428 ns / 6.09 µs / 9.40 µs, 128 workers 1.84 µs / 24.3 µs / 36.6 µs; at 64 blocks, 8 workers 99.7 ns / 789 ns / 960 ns, 32 workers 430 ns / 3.22 µs / 3.94 µs, 128 workers 1.73 µs / 15.7 µs / 18.5 µs; `round_robin` 191 / 220 / 234 ns and `least_loaded` 219 ns / 483 ns / 1.55 µs at 8 / 32 / 128 workers. `router_workload` per 1,000 requests: `kv_aware` 8.31 ms (`load_weight` 64) and 8.04 ms (`load_weight` 0), `round_robin` 13.3 ms, `least_loaded` 14.6 ms. Scaling: From 8 to 128 workers, 16 times as many, `kv_aware` grows 17.3x to 20.0x across the six request shapes, so selection is linear in workers. At 128 workers and 256 blocks, each worker costs 14 ns with nothing cached, 190 ns with 128 blocks matched, and 286 ns with 230 matched, about 1.2 to 1.4 ns per matched block above the 14 ns base; with nothing cached, 64 and 256 blocks cost the same, so the cost follows matched blocks, not request length. The whole workload ran faster under `kv_aware` (8.04 to 8.31 ms) than under the baselines (13.3 and 14.6 ms) even though it matches every worker; the likely cause is fewer blocks stored and evicted, which was not measured. Correctness is proven by the proptests in `tests/proptest_router.rs`: Under random worker states, every policy picks only healthy workers below capacity and returns `NoAvailableWorkers` exactly when none is eligible; `kv_aware` picks the lowest cost; with `load_weight` 0 it picks the maximum overlap; with `prefill_weight` 0 it picks the lowest load ratio, ties to the lowest worker id. Under random event streams, each worker's matched blocks equal a ground-truth model of its cache when workers remove only blocks nothing else extends, as leaf-only eviction does, and never exceed it when workers remove any block. Eleven injected bugs each fail at least one test. `tests/trace_fields.rs` records every field the router emits through a `tracing` layer and checks that the set equals the `avo-obs` names; run in parallel with the other tests in one process, it intermittently missed the debug-level fields, so it runs as its own test binary, cause not isolated.
- **Fix or Deferral:** Fixed for a single thread: KV-aware selection with configurable weights, deterministic ties (lower load ratio, then lower worker id), round-robin and least-loaded baselines, and worker health, load, and cache events. `avo-radix-index` gained `RadixTree::remove`, which drops a reported block and every block that extends it, since no prefix match can pass the missing block; the Milestone 3 proptest now covers it. Deferred: A shared multi-worker index (one tree whose nodes carry the set of workers holding each block), so one traversal scores every worker; exact removal, which needs those per-block worker sets to keep blocks below a removed one; softmax sampling; and concurrency. The cost adds blocks to a load ratio between 0 and 1, so `load_weight` must be on the block scale (64 here) for load to change a decision.
- **Dynamo Comparison:** Dynamo `main` at `35e2a66`. The indexer in `lib/router/kv-indexer` keeps one tree over all workers whose nodes carry the workers holding each edge, and `find_matches` returns an overlap score per worker from one traversal (`OverlapScores`); per-worker maps from block hash to tree node (`concurrent_radix_tree_compressed/lane_lookup.rs`) let cache events name blocks by hash alone: `Stored` with a parent hash and new blocks, `Removed` with block hashes, and `Cleared` (`lib/kv-events/src/event.rs`). Events here carry each block's full sequence, because these trees are keyed by path. The default cost in `lib/router/scheduler/src/selector/reference.rs` states both terms in blocks: `prefill_load_scale` times the larger of zero and (active prefill tokens plus request tokens, in blocks, minus overlap credit), plus decode cost blocks and an active-request term, where overlap credit weights device, host, and disk hits separately. The lowest cost wins with uniformly random ties at temperature 0, and a softmax sample over costs otherwise. This crate weights one load ratio, breaks ties deterministically, and counts every cached block alike, whatever its tier tag.

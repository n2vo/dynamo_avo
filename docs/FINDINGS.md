### Findings Log

Each milestone closes with one entry: The benchmark, the bottleneck that limits throughput or latency, the evidence, and the fix or the reason it was deferred, followed by the comparison against the Dynamo counterpart.

#### Milestone 1: Block Hashing

- **Benchmark:** `benches/hashing.rs`, Criterion, group `plh`, block size 16, unsalted, 1,024 / 8,192 / 32,768 tokens, on jeeves7 (M1 Max). Dynamo baseline times only `Request::positional_lineage_hashes(16)` on a prebuilt `Request`. Results in millions of tokens per second (Melem/s): Dynamo 260 to 275; `hash_sequence` 459 to 464; `IncrementalHasher` 252 to 268. Flat across lengths.
- **Bottleneck:** `IncrementalHasher::push` runs at about 0.57x of `hash_sequence` on the same tokens. Both share `chain_step` and `token_bytes`, so the difference is per-token entry cost: One bounds-checked `Vec::push`, one length compare, one branch, per token, versus one `chunks_exact` step per block. Hypothesis from code reading; not isolated by measurement.
- **Evidence:** Same outputs proven by the differential tests against `dynamo-kv-hashing` 1.5.1 and by the `incremental_matches_one_pass` proptest. Moving the token clone and `Request` build out of the Dynamo timed region changed its throughput by 2 to 4 percent, so the remaining gap is inside `into_blocks`.
- **Fix or Deferral:** Deferred. Decode produces one token per step, so the per-token path is the real one; batching through an `extend` would only help prefill. Candidate fixes: Replace the `Vec<u8>` allocation in `token_bytes` with a stack buffer sized by block, and let `push` write the token's bytes directly into that buffer instead of staging `u32` values. Revisit when a milestone exercises the decode path end to end.
- **Dynamo Comparison:** The xxh3 work is identical: Two hashes per block, same seeds, same little-endian layouts. The 1.7x throughput gap is structural, not algorithmic. `into_blocks` clones the full token vector, builds a `TokenBlockSequence` with one `TokenBlock` per block, each owning a copy of its tokens and both hashes, collects a `Vec<UniversalBlock>`, and then maps that into the returned hashes. Dynamo materializes block objects because its router, pool, and migration paths consume them; the hash is a by-product. `avo-kv-hash` computes only the hash. When later milestones require block objects, that cost returns.

#### Milestone 2: Block Pool

- **Benchmark:** `benches/pool.rs`, Criterion, group `pool`, capacities 1,024 / 8,192 / 32,768 blocks, on jeeves7 (M1 Max). `alloc_drop` allocates and drops an uncommitted block (free-list path). `lookup_hit` looks up a committed inactive block and drops the handle (hash-index path). `evict` allocates on a pool whose blocks are all inactive, so every allocation evicts, then commits under a fresh hash and drops. Medians after the fix: `alloc_drop` 20.5 ns; `lookup_hit` 24.6 ns; `evict` 66.8 ns, 66.9 ns, and 71.4 ns.
- **Bottleneck:** The first implementation found the least recently used (LRU) block by scanning every entry of `blocks` for the smallest `last_use`, so eviction was O(n) in capacity at about 0.7 ns per block: 762 ns, 6.06 µs, and 23.1 µs at the three capacities. At 32,768 blocks one eviction cost as much as about 1,100 free-list allocations, and once the pool fills, every allocation evicts.
- **Evidence:** Before the fix, eviction time grew 7.95x for an 8x increase in capacity and 3.81x for 4x, while the free-list and lookup paths stayed flat. Pool correctness under random allocate, commit, lookup, clone, and drop sequences is proven by `no_block_leaked_or_freed_twice`. During the fix it caught a missing link update in `lru_unlink`; the failing sequence is saved in `properties.proptest-regressions` and replays on every run.
- **Fix or Deferral:** Fixed. Inactive blocks are kept in an intrusive doubly linked list indexed by block id (`prev`, `next`, `head`, `tail`): release appends at the tail, a lookup hit unlinks from anywhere, and eviction pops the head, all O(1) with no allocation. Eviction is now flat at 67 to 71 ns, 11x to 323x faster. The cost is about 2 ns on `lookup_hit` (22.5 to 24.6 ns), one unlink and one push per revive. The same change fixed a stale-index bug: Evicting a block deleted the hash-index entry unconditionally, so if a newer block had been committed under the same hash, its entry was removed and it became unreachable. Eviction now removes the entry only if it still points at the evicted block; `evicting_a_replaced_block_keeps_the_newer_index_entry` covers it.
- **Dynamo Comparison:** Dynamo `main` at `4435cab`, `lib/kvbm-logical/src/pools/inactive`. The inactive pool is pluggable: HashMap with first-in-first-out (FIFO) reuse (`BTreeMap`, O(log n)), LRU (`lru` crate, O(1) `pop_lru`), multi-LRU (four LRU tiers bucketed by TinyLFU access frequency, coldest tier evicted first), and Lineage. The default when none is configured is Lineage with Tick ordering, which evicts only leaves of the prefix lineage graph, ordered in a `BTreeMap` by insertion tick (O(log n)); a Fifo variant is O(1) with no steady-state allocation, the same shape as the list here. No backend scans. The remaining difference is leaf-only eviction: `avo-block-pool` can evict a parent block while its children stay cached, and because prefix matching stops at the first miss, those children become unreachable while still holding capacity. Milestone 3's radix index restricts eviction to leaves, with this list as the ordering among them.

#### Milestone 2: Block Pool Concurrency

- **Benchmark:** `benches/contention.rs`, Criterion, group `contention`, 1 / 2 / 4 / 8 threads on a 4,096-block pool, on jeeves7 (M1 Max). `churn`: Each thread allocates (evicting once the pool is full), commits under a thread-unique hash, and drops. `lookup`: Each thread looks up one of 1,024 shared committed blocks and drops the handle. One element is one cycle by one thread and time runs from barrier release to the last join, so results are total throughput across threads; ideal scaling doubles when threads double. Medians with `std::sync::Mutex`, in millions of cycles per second: `churn` 15.0, 8.19, 4.67, 3.82; `lookup` 39.5, 16.8, 7.44, 7.47.
- **Bottleneck:** One `Mutex<PoolState>` guards the whole pool, and every operation takes it: `allocate`, `commit`, `lookup`, `hash`, and every handle clone and drop. Total throughput falls as threads are added instead of rising: 3.9x lower for `churn` and 5.3x lower for `lookup` at 8 threads than at 1. The pool serializes on the lock, and the added threads pay handoff cost on top.
- **Evidence:** The same decline at every step from 1 to 4 threads on both workloads, with `lookup` flat from 4 to 8, is inferred as the signature of a single contended lock rather than of the work inside it; the single-thread paths measure 20 to 25 ns in `benches/pool.rs`. Correctness under contention is proven by `invariants_hold_under_concurrent_use`: Eight workers run 20,000 seeded operations each over 32 shared hashes on a 64-block pool while a checker thread audits the free, active, inactive partition under the lock, and nothing is active after every handle drops. The first version of that test hung instead of failing when a worker panicked, because the checker was never told to stop; the fixed version joins every worker, stops the checker, then re-raises the first worker panic with `resume_unwind`. With an injected bug it fails in under a second.
- **Fix or Deferral:** Fixed in two steps; the second is planned. Step 1: `std::sync::Mutex` replaced by `parking_lot::Mutex`, which also removes the poison-recovery path in `lock`, since `parking_lot` has no lock poisoning. Medians after: `churn` 18.1, 12.7, 9.26, 4.04; `lookup` 51.1, 24.0, 17.3, 11.8. Gains of 1.21x, 1.56x, 1.98x, 1.06x for `churn` and 1.29x, 1.43x, 2.33x, 1.58x for `lookup`. The collapse remains: 1 to 8 threads still falls 4.5x for `churn` and 4.3x for `lookup`, and `churn` at 8 threads is within noise of before, because the lock is cheaper to take but still taken once per operation. Why `parking_lot` gains most at 4 threads was not isolated by measurement. Step 2, planned: Batch APIs that take the lock once per call, `allocate_many(n)` and `lookup_prefix(&[u64])`, with batch workloads added to this benchmark and measured against the step 1 numbers above. Moving handle reference counts off the lock is not planned.
- **Dynamo Comparison:** Dynamo `main` at `4435cab`. `BlockStore` (`lib/kvbm-logical/src/pools/store.rs`) has the same shape: All state behind one `parking_lot::Mutex` (`inner: Mutex<BlockStoreInner<T>>`). Dynamo's lever is batching, not a finer lock: `match_blocks` in `lib/kvbm-logical/src/manager/mod.rs` takes one store-lock acquisition for an entire active plus inactive prefix through `BlockStore::match_prefix_locked_batch`, a scattered variant does the same for non-prefix probes, and TinyLFU frequency updates run outside the lock. Dynamo's handles also avoid the store lock on clone and take it only when the last reference drops. Step 1 here matches Dynamo's lock; step 2 matches its batching.
